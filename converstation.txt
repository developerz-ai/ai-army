How OpenClaw Works (the relevant bits)
OpenClaw runs a Gateway (control plane) on your machine that connects to messaging channels (Slack, Discord, Telegram, WhatsApp, etc.). The core architecture is:

Identity files — all plain markdown in a workspace directory: SOUL.md (personality/values), IDENTITY.md (presentation/name/tone), AGENTS.md (behavior instructions), USER.md (user context), TOOLS.md (local notes). These get injected into the system prompt at session start.

Multi-agent routing — one Gateway can run multiple agents, each with isolated workspaces, auth profiles, sessions, and skills. Inbound messages are routed via bindings (most-specific match wins: specific peer > guild/server > channel > default).

Session management — each conversation gets a session keyed as agent:<agentId>:<mainKey>. Sessions accumulate context until compaction kicks in (summarizes old turns, flushes important stuff to memory files on disk before truncating). There's a memoryFlush mechanism that prompts the agent to write critical context to memory/YYYY-MM-DD.md before compaction erases it.

Models — configured as provider/model strings (e.g., anthropic/claude-sonnet-4-5). Supports failover chains, model allowlists with aliases, and custom providers via OpenAI-compatible endpoints (OpenRouter, LMStudio, Fireworks, etc.).

MCP — still evolving (the native MCP issue was closed as "not planned" in favor of skills-based MCP integration), but there's a community skill that bridges MCP servers. The config pattern uses the standard mcpServers block with command, args, env, and status.

Skills — folders containing SKILL.md + optional scripts, following the AgentSkills spec. Per-agent via workspace skills/ folder, with shared skills possible.

You want something simpler and more declarative: one config file that defines N bots, each with its own channel auth, model config, soul file, MCP servers, and skills. Key design decisions I'm proposing vs OpenClaw
One bot = one channel. OpenClaw does complex binding-based routing (one gateway, many channels, many agents). I'm suggesting keeping it flat: each bot object has exactly one channel block. If you want the same personality on Slack and Discord, you define two bots with the same soul file. Simpler to reason about, simpler to debug.

Providers are a shared pool. You define auth once in providers, then reference by name. Multiple bots can share "anthropic-main" without duplicating keys.

MCP servers are also a shared pool. Define once, attach by name per bot. This avoids spawning duplicate MCP server processes — the runtime can share them.

sessionPer replaces OpenClaw's complex session keying. Instead of session key formulas, you just declare: do conversations split per user, per channel/room, or per thread?

Env var interpolation with ${VAR} syntax. Secrets never live in the JSON. The runtime resolves them at startup.

No heartbeat/cron in v1. OpenClaw's heartbeat system is powerful but complex. I'd add it later as an optional block per bot.

What the runtime does (implementation-wise)
For each bot in the config, the program:

Reads the SOUL.md → injects it as the system prompt
Connects to the channel (Slack Bolt SDK / Discord.js)
On each message, resolves the user → finds or creates a session (per-user, per-channel)
Calls the Claude Agent SDK's query() with the user's message, passing allowedTools, permissionMode, mcpServers, sandbox, and the system prompt
Streams the response back to the channel
On session length threshold → compaction (summarize + flush to memory dir)

The mounts let you expose extra read-only or read-write directories — like mounting /repos so the work bot can read your code, or /var/log/apps so the devops bot can grep logs.

Between restarts, everything survives. The bot picks up where it left off by reading its session transcripts and memory files.

Two sandbox modes
just-bash — the safe default. A simulated bash environment with an in-memory virtual filesystem, written in TypeScript. Designed for AI agents that need a secure, sandboxed bash environment.
GitHub
 No real shell process, no binary execution, no network by default. Perfect for the family bot or any bot that just needs to read/search files.

docker — real isolation. Spins up a container per bot with the specified image, installs packages, mounts the workspace. The bot gets a real shell, real apt-get, real python3. Network is controlled via allowedDomains. Container persists (not ephemeral) so installed packages and state survive.
